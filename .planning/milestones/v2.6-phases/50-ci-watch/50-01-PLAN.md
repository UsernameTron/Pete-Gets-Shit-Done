Create `lib/ci-patterns.json` as a JSON array of pattern objects. Each object has these fields:

```json
{
  "source": "<regex pattern string>",
  "flags": "i",
  "category": "<category name>",
  "description": "<human-readable description of the failure>",
  "fix": "<concrete fix suggestion text>"
}
```

Seed with these 6 patterns (D-10 specifies 4 as baseline; we add 2 additional high-value patterns for a total of 6):

1. EXDEV cross-device rename:
   - source: `EXDEV.*cross.device`
   - category: `cross-device`
   - description: `Cross-device rename failed (EXDEV) — typically moveSync across filesystem boundaries`
   - fix: `Use copySync + removeSync fallback instead of moveSync/renameSync. See lib/phase.cjs for the established pattern.`

2. Missing module / Cannot find module:
   - source: `Cannot find module|MODULE_NOT_FOUND`
   - category: `missing-module`
   - description: `Required module not found — likely missing dependency or wrong path`
   - fix: `Run npm install. If the module is a local file, check the require path is correct relative to the executing file.`

3. GitHub Actions SHA pin mismatch:
   - source: `Unable to resolve action.*uses.*@`
   - category: `sha-pin`
   - description: `GitHub Actions step references an invalid or outdated commit SHA`
   - fix: `Update the SHA pin in the workflow YAML. Use the tag page on GitHub to find the correct full SHA for the version you want (e.g., actions/checkout v4).`

4. Node version incompatibility:
   - source: `SyntaxError.*Unexpected token|node:|--experimental-|engine.*"node".*incompatible`
   - category: `node-version`
   - description: `Code uses syntax or APIs not available in the running Node.js version`
   - fix: `Check the engines field in package.json and the CI matrix. Ensure the CI matrix only includes supported Node.js versions (currently 20 and 22).`

5. Test assertion failure (generic):
   - source: `not ok \\d|FAIL |AssertionError|expected.*to.*equal`
   - category: `test-failure`
   - description: `One or more test assertions failed`
   - fix: `Read the specific test name and assertion message. Compare expected vs actual values. Check if the test or the implementation needs updating.`

6. Exit code non-zero:
   - source: `exit code \\d+|Process exited with code|exited with \\d+`
   - category: `exit-code`
   - description: `A process exited with a non-zero exit code`
   - fix: `Check the command that failed in the log output above this line. The exit code indicates the type of failure.`

The file must be valid JSON. No trailing commas. Follow the exact same structural convention as `lib/injection-patterns.json` (array of objects, `source`/`flags` fields for regex).

  <action>
Create `get-shit-done/workflows/ci-watch.md` following the established workflow pattern (purpose tag, process tag, step tags).

The workflow must implement these steps:

**Step 1: detect_branch**
Get current branch via `git branch --show-current`. If detached HEAD, error and exit. Store as `$BRANCH`.

**Step 2: initial_poll**
Run `gh run list --branch "$BRANCH" --limit 10 --json databaseId,name,status,conclusion,url,createdAt` to get current runs. Parse JSON output. If no runs found, tell user "No CI runs found for branch $BRANCH" and exit.

**Step 3: polling_loop**
Poll continuously at the configured interval (default 15 seconds, per D-02). On each poll:

1. Run the same `gh run list` command from step 2
2. For each run, track: databaseId, name, status, conclusion, url
3. Display streaming status line (per D-03, D-14): a progress line like:
   ```
   CI Watch: 2/3 runs complete (1 pass, 1 fail) — polling in 15s...
   ```
4. Check if ALL runs have reached terminal state (status === "completed")
5. If all terminal, break the loop
6. If not all terminal, wait the interval and poll again

Handle SIGINT (Ctrl+C) per D-04: print whatever results are available at that point and exit cleanly.

**Step 4: format_results**
Build a GSD-formatted results table (per D-13, D-15):

```
+---------------------------+--------+----------+------------------------------------------+
| Job                       | Status | Duration | URL                                      |
+---------------------------+--------+----------+------------------------------------------+
| test (ubuntu-latest, 20)  | pass   | 2m 31s   | https://github.com/.../runs/12345        |
| test (ubuntu-latest, 22)  | pass   | 2m 45s   | https://github.com/.../runs/12346        |
| test (macos-latest, 22)   | FAIL   | 1m 12s   | https://github.com/.../runs/12347        |
+---------------------------+--------+----------+------------------------------------------+
```

Display the table.

If all runs passed: print summary line "All CI runs passed." and exit.

If any runs failed: continue to step 5.

**Step 5: fetch_failed_logs**
For each failed run (per D-06):

```bash
gh run view <databaseId> --log-failed
```

Capture the output. Do NOT dump the raw log (per D-05). Instead, extract error lines by searching for these markers (per D-07):
- Lines containing "not ok"
- Lines containing "FAIL"
- Lines containing "Error:"
- Lines containing "exit code"
- Lines containing "AssertionError" or "AssertionError"

Keep at most 30 error-relevant lines per failed run.

**Step 6: diagnose_and_suggest**
For each failed run's extracted error lines (per D-08, D-09):

1. Load `lib/ci-patterns.json` (the pattern library from this repo — path relative to GSD install root: `$HOME/.claude/get-shit-done/lib/ci-patterns.json`)
2. Test each pattern's regex against the extracted error text
3. If a pattern matches (per D-09 tier 1): use its `description` and `fix` fields
4. If no pattern matches (per D-09 tier 2, D-12): present the extracted error lines and ask Claude to analyze and suggest a fix

**Step 7: format_failure_report**
For each failed run, display below the results table (per D-16):

```
## Failed: test (macos-latest, 22)

**Error:**
  tests/unit/core.test.cjs > test name here
  AssertionError: expected 3 to equal 4

**Diagnosis:** One or more test assertions failed
**Suggested Fix:** Read the specific test name and assertion message. Compare expected vs actual values.
```

Include the matched pattern category if available, or "LLM analysis" if pattern matching fell through.

**Important implementation notes:**
- The workflow is a prompt for Claude to execute, written in markdown with step tags — NOT JavaScript code
- Use `bash` code blocks for the commands Claude should run
- The polling loop should use `sleep 15` (or configured interval) between polls
- Duration calculation: compare createdAt to current time, or use `gh run view <id> --json updatedAt,createdAt` for precise timing
- All `gh` commands should handle errors (gh not installed, not authenticated, no repo)
