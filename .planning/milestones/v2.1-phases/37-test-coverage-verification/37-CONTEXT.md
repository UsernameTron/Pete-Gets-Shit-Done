<decisions>
## Implementation Decisions

### install.js Coverage Strategy
- **D-01:** Use targeted 80% push approach — write tests for high-risk utility functions and conversion logic in `bin/install.js` (currently 68.13%). Skip testing interactive CLI prompts, `readline` flows, and pure I/O glue. Focus on the 116 exported/testable functions, especially runtime converters (Codex, Copilot, Cursor, Antigravity, Windsurf, Gemini) and path/config utilities.

### Coverage Gap Prioritization
- **D-02:** Sequence for maximum efficiency — quick wins first to lift overall above 90%, then backfill the big file:
  1. `build-hooks.js` (79.26% -> 80%+) — ~5 lines, quick win
  2. `state.cjs` (89.48% -> 90%+) — ~5 lines
  3. `uat.cjs` (88.65% -> 90%+) — ~10 lines
  4. `phase.cjs` (87.93% -> 90%+) — ~15 lines
  5. `workstream.cjs` (80.24% -> 85%+) — ~20 lines
  6. `profile-pipeline.cjs` (83.11% -> 88%+) — ~25 lines
  7. `install.js` (68.13% -> 80%+) — ~630 lines, largest effort

### Branch Coverage
- **D-03:** Line/statement coverage only per ROADMAP.md success criteria. No formal branch coverage threshold. Branch coverage improves naturally as line-coverage tests are written (e.g., `workstream.cjs` at 45% branch will improve as its 80% -> 85% line push covers more conditionals).

### Claude's Discretion
- install.js: specific function targeting and test file organization
- Coverage priority order within each module (which uncovered lines to target first)
- Whether to create new test files vs. extend existing ones for each module
- Test naming and grouping conventions (follow existing patterns)
