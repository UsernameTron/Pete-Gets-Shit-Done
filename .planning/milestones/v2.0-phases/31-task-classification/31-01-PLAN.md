# PLAN — Phase 31.1: classify.cjs Module — Task Classification & Adaptive Gates

## Objective

Create the `classify.cjs` module as a Layer 0 foundation module (no intra-project dependencies). Implements three exported functions: `classifyTask()`, `extractSignals()`, and `adaptWorkflowGates()`, plus exported constants `COMPLEXITY_LEVELS` and `PHASE_TYPE_KEYWORDS`.

## Architecture Constraints

- **Layer 0**: No `require('./core.cjs')`, no `require('./config.cjs')`, no intra-project deps. Only Node.js builtins allowed.
- **Zero external dependencies**: CommonJS, no npm packages.
- **deepFreeze convention**: All exported constant objects must be frozen.
- **Pure functions**: All functions are deterministic given their inputs. No file I/O, no side effects.

## Task 2: extractSignals(phaseInfo, planInventory, context) — INTEL-08

Returns a signals object with:

- `file_count` — Number of files from plan inventory (`files_to_modify` arrays if available, else plan count as proxy)
- `requirement_count` — Number of requirement IDs (from `context.reqIds` string, comma-separated)
- `phase_type` — Derived from phase name via PHASE_TYPE_KEYWORDS matching (first keyword match wins, default: 'execution')
- `dependency_depth` — Count of plans with `depends_on` arrays (from planInventory frontmatter if available, else 0)
- `historical_failure_rate` — From `context.failureRate` if provided (Phase 32 will supply this), else null
- `plan_count` — Number of plans in planInventory

All fields have safe defaults for null/undefined inputs. Function never throws.

## Task 3: classifyTask(phaseInfo, planInventory, context) — INTEL-07

### Weighted Scoring Algorithm

1. Call `extractSignals(phaseInfo, planInventory, context)` to get raw signals
2. Compute weighted complexity score (0-10 scale):

| Signal | Weight | Scoring |
|--------|--------|---------|
| plan_count | 2.0 | 0-1 plans: 0, 2-3: 1, 4-6: 2, 7+: 3 |
| requirement_count | 2.0 | 0-2: 0, 3-5: 1, 6-8: 2, 9+: 3 |
| phase_type | 1.5 | research/documentation: 0, execution: 1, verification/integration: 2 |
| dependency_depth | 1.0 | 0: 0, 1-2: 1, 3+: 2 |
| historical_failure_rate | 1.5 | null/0: 0, 0.01-0.20: 1, 0.21-0.50: 2, 0.51+: 3 |

3. Normalize: `raw_score = sum(signal_score * weight)` (max possible ~24 when all at max)
4. Map to complexity level using thresholds on raw_score:
   - raw_score < 3: trivial
   - raw_score < 6: standard
   - raw_score < 10: complex
   - raw_score >= 10: critical

5. Confidence calculation:
   - Start at 0.5 (base)
   - +0.1 for each non-null signal (up to 5 signals = +0.5)
   - Cap at 1.0
   - If only plan_count and requirement_count are available (no history, no dependency depth), confidence stays around 0.6-0.7

### Return value
```js
{
  complexity: 'standard', // one of COMPLEXITY_LEVELS values
  signals: { /* extractSignals output */ },
  confidence: 0.7,        // 0-1 float
}
```

## Task 4: adaptWorkflowGates(taskContext, config) — INTEL-09

Takes:
- `taskContext` — Result of `classifyTask()` (has `.complexity`, `.signals`, `.confidence`)
- `config` — The loaded GSD config object

Returns an object with config override keys. If `config.adaptive` is falsy, returns empty object `{}` (feature flag gate).

### Adaptation rules by complexity:

**trivial:**
- `skip_research: true` — Skip research phase for trivial tasks
- `plan_checker_enabled: false` — Skip plan verification
- `verification_rigor: 'light'` — Lighter verification

**standard:**
- Returns `{}` (no overrides — standard is the baseline)

**complex:**
- `verification_rigor: 'thorough'` — More thorough verification
- `parallelization_wave_size: 2` — Smaller waves for more careful execution

**critical:**
- `verification_rigor: 'thorough'`
- `parallelization_wave_size: 1` — Sequential execution for maximum safety
- `force_quality_tier: true` — Signal to routing layer

If `taskContext` is null/undefined, returns `{}`.
