# PLAN -- Phase 33.2: Config Migration v1 -> v2

## Objective

Add a config migration (from: 1, to: 2) that ensures existing v1 configs get the new intelligence layer keys (`routing_strategy`, `adaptive`) injected with safe defaults. Bump `CONFIG_VERSION` to 2. No existing user's config.json breaks.

## Architecture Constraints

- **Migration registry pattern**: Add entry to `configMigrations` array in core.cjs (line ~366).
- **CONFIG_VERSION bump**: Change `const CONFIG_VERSION = 1` (line 364) to `const CONFIG_VERSION = 2`.
- **Safe defaults**: `routing_strategy: 'static'` and `adaptive: false` — existing behavior unchanged.
- **loadConfig() defaults already correct**: Lines 418 and 434 already have `routing_strategy: 'static'` and `adaptive: false` in the defaults object. The migration ensures persisted config.json files get these keys added.
- **Idempotent**: If keys already exist in user's config, do NOT overwrite them. Only add missing keys.
- **Write-back**: `runConfigMigrations()` (line 390) already handles writing the migrated config back to disk. The migration function just mutates the parsed object.

## Task 1: Add Migration Entry to configMigrations

### Location

`get-shit-done/bin/lib/core.cjs`, lines 366-388. Add new entry after the existing `from: 0, to: 1` migration.

### Implementation

```js
{
  from: 1, to: 2,
  migrate(parsed, _cwd) {
    // Add intelligence layer defaults for existing v1 configs
    if (!('routing_strategy' in parsed)) {
      parsed.routing_strategy = 'static';
    }
    if (!('adaptive' in parsed)) {
      parsed.adaptive = false;
    }
  },
},
```

### Why this works

1. User with v0 config (no `config_version` key) -> runs migration 0->1, then 1->2. Gets depth->granularity migration AND intelligence layer keys.
2. User with v1 config (`config_version: 1`) -> runs migration 1->2 only. Gets intelligence layer keys added.
3. User with v2 config (`config_version: 2`) -> `runConfigMigrations()` early-returns at line 392 (`version >= CONFIG_VERSION`). No mutation.
4. User who already set `routing_strategy: 'dynamic'` in their v1 config -> the `in` check preserves their choice. Only missing keys get defaults.

## Task 3: Unit Tests -- tests/core.test.cjs

Add test cases to the existing `core.test.cjs` file, within or adjacent to the existing migration test section.

### Test Cases (~8 tests)

**describe('Config migration v1 -> v2')**

1. **v1 config gets routing_strategy and adaptive added**: Create config.json with `{ config_version: 1, model_profile: 'balanced' }`. Call `loadConfig()`. Verify returned config has `routing_strategy: 'static'` and `adaptive: false`. Verify config.json on disk now has `config_version: 2`.

2. **v1 config preserves existing routing_strategy**: Create config.json with `{ config_version: 1, routing_strategy: 'dynamic' }`. Call `loadConfig()`. Verify `routing_strategy` is still `'dynamic'` (not overwritten to `'static'`).

3. **v1 config preserves existing adaptive**: Create config.json with `{ config_version: 1, adaptive: true }`. Call `loadConfig()`. Verify `adaptive` is still `true`.

4. **v0 config runs both migrations**: Create config.json with `{ depth: 'comprehensive' }` (no config_version). Call `loadConfig()`. Verify: `granularity: 'fine'` (from 0->1), `routing_strategy: 'static'` (from 1->2), `config_version: 2`.

5. **v2 config is not mutated**: Create config.json with `{ config_version: 2, routing_strategy: 'auto', adaptive: true }`. Call `loadConfig()`. Verify config_version still 2, routing_strategy still 'auto', adaptive still true. Verify config.json on disk is NOT rewritten (compare mtime or content).

6. **Missing config.json returns defaults with v2 keys**: Call `loadConfig()` with no config.json. Verify returned config has `routing_strategy: 'static'`, `adaptive: false` from defaults object.

7. **Migration is idempotent**: Run `loadConfig()` twice on same v1 config. Second call should be a no-op (config_version already 2 after first call).

8. **CONFIG_VERSION is 2**: Import core.cjs or read the constant. Assert `CONFIG_VERSION === 2`. This catches accidental version changes.

### Test Setup

Each test creates a temporary directory with `.planning/config.json`, calls `loadConfig(tmpDir)`, then verifies both the returned object and the persisted file.
