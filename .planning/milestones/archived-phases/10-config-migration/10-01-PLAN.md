# Plan 10-01: Config Migration System

## Objective

Add config version tracking and a structured migration pipeline to `loadConfig` in core.cjs, replacing ad-hoc inline migrations with a versioned, forward-compatible system.

## Current State

- `loadConfig()` in core.cjs handles two inline migrations:
  1. `depth` → `granularity` (lines 232-238)
  2. `multiRepo: true` → `sub_repos[]` (lines 243-253)
- No version field in config.json
- Each migration is a one-off conditional block — no sequencing, no version tracking

## Design

### Config Version Field
Add `config_version: number` to config.json. Unversioned configs are treated as version 0.

### Migration Registry
Array of migration objects `{ from: number, to: number, migrate: (parsed) => parsed }`, executed sequentially from current version to latest.

### Migrations
- **v0 → v1**: Extract existing `depth` → `granularity` migration
- **v0 → v1**: Extract existing `multiRepo` → `sub_repos` migration
- Both already exist inline; refactor them into the registry

### Rules
- Migrations are idempotent (safe to re-run)
- Config is written back to disk after migration with updated version
- Unknown versions are left alone (forward-compatible)
- Migration errors are caught and logged but don't break config loading

## Tasks

### Task 1: Add migration registry to loadConfig

1. Define `CONFIG_VERSION = 1` constant
2. Create `migrations` array with v0→v1 entry that combines existing depth and multiRepo migrations
3. Add migration runner: detect current version, run applicable migrations sequentially, update `config_version`
4. Replace inline migration blocks with the registry call
5. Preserve all existing behavior exactly

### Task 2: Add tests for migration system

1. Test: unversioned config gets migrated to v1 with correct version stamp
2. Test: config already at v1 skips migration
3. Test: depth + multiRepo both migrated in single pass
4. Test: migration error doesn't break config loading
5. Test: unknown future version (v99) left alone

## Success Criteria

- `loadConfig` uses versioned migration pipeline instead of inline conditionals
- `config_version` field added to config.json after first load
- All existing tests still pass
- New tests cover migration versioning
- No behavior change for end users
