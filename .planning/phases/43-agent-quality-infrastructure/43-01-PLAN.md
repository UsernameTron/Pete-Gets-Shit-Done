<task type="auto">
  <name>Task 1: Add 4D scoring rubric to gsd-verifier (QUAL-01)</name>
  <files>agents/gsd-verifier.md</files>
  <action>
Add a new `<scope_rubric>` section to gsd-verifier.md after the existing `<scope_general>` section block. This adds a 4D architecture scoring rubric that the verifier applies during general-scope verification.

The rubric has 4 dimensions with weights:
- Security (35%): prompt injection resistance, permission boundaries, secret handling, input validation
- Performance (25%): resource bounds, lazy loading, timeout config, caching strategy
- Correctness (25%): error handling, edge cases, type safety, test coverage
- Maintainability (15%): naming clarity, single responsibility, documentation, dependency hygiene

14 design pattern criteria total (roughly 3-4 per dimension).

Scoring: each criterion is 0-10. Dimension score = weighted average of its criteria. Total = weighted sum of dimensions. Threshold: >= 70 overall, no dimension below 50.

Output format in VERIFICATION.md:
```
## Architecture Score

| Dimension | Weight | Score | Status |
|-----------|--------|-------|--------|
| Security | 35% | 82 | PASS |
| Performance | 25% | 71 | PASS |
| Correctness | 25% | 68 | PASS |
| Maintainability | 15% | 75 | PASS |
| **Overall** | **100%** | **74.8** | **PASS** |
```

Also add instructions in the general scope section to invoke the rubric after goal-backward verification completes.
  </action>
</task>

Create a new reference document at `get-shit-done/references/agent-necessity-gate.md`.

Structure:
```
# Agent Necessity Gate

Three-part gate that runs before any new agent proposal...

## Gate Checks

### 1. Context Pollution
Would doing this inline pollute the main context window?
- PASS: Task produces >2000 tokens of intermediate output, or reads >5 files
- FAIL: Task is small and self-contained

### 2. Parallelizability
Can this run in parallel with other work?
- PASS: Independent of current conversation state
- FAIL: Requires sequential access to shared state

### 3. Specialization
Does it need specialized tools, permissions, or isolation?
- PASS: Needs different tool set, model, or permission mode
- FAIL: Same tools and permissions as the caller

## Outcomes
- PASS (all 3 pass): Create the agent
- FAIL (any fail): Inline is correct — do not create agent
- AMBIGUOUS (mixed): Prompt user for decision

## Decision Matrix
[Table mapping combinations to outcomes]

## Examples
[3 examples: one PASS, one FAIL, one AMBIGUOUS]
```

Extend the verify-work workflow to support mode selection. Add argument parsing for `--mode=compliance` and `--mode=schema` at the initialize step.

Mode 1 (compliance — existing behavior): Does implementation match the plan? This is the current UAT flow.

Mode 2 (schema quality — new): Does it follow GSD conventions? Checks:
- Frontmatter presence and required fields in agent files
- Commit message format (type(scope): description)
- File locations match GSD directory conventions
- Test files exist for new code
- SUMMARY.md created for each plan

Default (no flag): Both modes run. Schema check runs first as a pre-flight, then compliance UAT.

Add a new step `schema_check` that runs before `find_summaries` when mode includes schema. The schema check is automated (no user interaction needed) and produces a schema report section in the UAT file.
