"Tests pass locally" is not sufficient — CI must be green. Triggered by: multiple PRs shipped while CI checks were still pending or failing.
- [2026-04-09] [Spec vs Reality]: When a design spec line contradicts observable on-disk state, trust reality over the spec and flag the delta back to the operator. Do not literally implement a spec that is provably wrong. Triggered by: `deriveSlug` spec said `'-' + cwd.replaceAll('/', '-')` which double-dashes absolute paths; the actual Claude Code project slug at `~/.claude/projects/-Users-cpconnor-projects-Pete-Gets-Shit-Done/` uses a single leading dash. Shipped the bug into test-runner instead of catching it while writing the function.
- [2026-04-09] [Signal Detection]: Correction-phrase gates must distinguish instructional mentions ("don't touch X", "stop at Layer 1") from actual corrections ("don't do that — you're wrong"). Bare keyword matching on "don't"/"stop"/"no,"/"correction" inflates signal counts inside normal planning text. Fix: require a preceding corrective marker (e.g., phrase must follow "you" or start a sentence after a rebuttal), or drop the weakest phrases from the set, or weight by position in a user turn that follows an assistant turn. Triggered by: the lesson-capture gate fired with 6 signals on its own introduction session, where the only real correction was the deriveSlug fix.
- [2026-04-10] [Signal Detection]: Audit methodology must match artifact taxonomy before flagging findings. Before any "source has X, installer missing X" finding, confirm the two sides of the comparison are the same artifact type. Document the artifact taxonomy (commands vs workflows vs agents vs hooks vs skills) at the top of the audit report so the methodology is auditable. Add a pre-flight check to extension-auditor prompts that enumerates artifact categories and requires the auditor to declare which category each finding applies to before flagging it. Triggered by: Phase 36 audit compared source workflows/ (internal orchestration, 56 files) against bin/install.js command registrations (user-facing slash commands in commands/gsd/, 62 files) — a category error that produced a false positive tech debt item requiring a post-audit addendum.
- [2026-04-13] [Integration]: lesson-capture-gate.cjs shipped in PR #34 with code + tests but was never registered in settings.json Stop hooks. Hook was inert for 3 days and all of v2.2. Integration checklists for hooks must include a verify-registration step. Triggered by: Pete discovered the hook was never wired into settings.json.
- [2026-04-10] [Hook Design]: Stop hooks can race ahead of human-review gates in interactive prompts. When a prompt includes an explicit "do not commit yet" instruction, the uncommitted-files Stop hook should not force a commit — it cannot distinguish "user forgot to commit" from "user is mid-review and explicitly deferred committing." Fix: add a sentinel file or environment flag (e.g., .planning/.review-pending) that the uncommitted-files Stop hook checks; if the sentinel exists, the hook should allow uncommitted state or require stash instead of commit. File a follow-up task in the GSD backlog. Triggered by: during v2.1 audit correction, Pete asked to see the diff before committing, but the Stop hook fired and forced a commit before he could review.
- [2026-04-24] [Repo Governance]: Branch protection requires BOTH `required_status_checks` AND `required_pull_request_reviews`. Status checks alone only gate PR merges — direct pushes bypass CI entirely. For single-dev repos, set `required_approving_review_count: 0` to force the PR path without human approval (~30s overhead per commit batch). Triggered by: Second Brain v1.4 Phase 17-03 — protection appeared configured in GitHub UI but direct pushes to master were ungated.
- [2026-04-24] [API Safety]: GitHub branch protection API uses PUT, not PATCH — it replaces the entire protection config. Always read current settings, merge changes, then PUT the full object. Partial updates silently wipe existing settings. Triggered by: Second Brain Phase 17-03 fix attempt nearly removed existing status checks.
- [2026-04-24] [Verification]: Acceptance criteria that claim enforcement ("CI gates master") must be tested by attempting the blocked action, not by confirming the setting appears in the UI. The UI shows configuration, not enforcement. Triggered by: Phase 17-03 acceptance criteria passed visually while enforcement was cosmetic.
- [2026-05-08] [Drift/Tolerance]: When designing drift gates that compare floating-point measurements (coverage percent, timing, memory), epsilon must absorb legitimate cross-platform variance (~0.05–0.1% for c8 coverage across macOS vs ubuntu). 0.01% is too tight; ship-time tests pass on the dev's local OS but fail on CI's OS for the same SHA. **Why:** c8 instrumentation differs subtly across OS filesystems (case sensitivity, .DS_Store inclusion, symlinks). **How to apply:** Default percentage-comparison epsilon to 0.1 and accept the slightly looser gate; if you need tighter, use a per-claim override and document why. Triggered by: Phase 57-03 PR — local check-doc-drift returned 91.63%, CI ubuntu/22 returned 91.69148%, 0.01 epsilon flagged the 0.06% delta as drift, blocking the PR's docs-integrity gate.
- [2026-05-08] [Spec vs Reality / Status Checks]: GitHub Actions status-check context names include all matrix dimensions, not just the human-readable subset. A workflow with `matrix: { os, node-version, full_suite }` produces contexts like `test (ubuntu-latest, 22, true)`, not `test (ubuntu-latest, 22)`. Branch-protection PATCH commands that use the truncated form silently break — GitHub waits forever for jobs that never report under those names. **Why:** The "actual job name" lives only in `gh api repos/.../branches/main/protection` output; documents written from memory often drop the trailing matrix value. **How to apply:** Before authoring or running any branch-protection PATCH, run `gh api repos/$OWNER/$REPO/branches/$BRANCH/protection -q '.required_status_checks.contexts'` and copy names verbatim. Lesson 2026-04-09 [Spec vs Reality] applied. Triggered by: Phase 57-03 SUMMARY's documented PATCH used 2-element check names that didn't match reality; would have replaced 4 working contexts with 5 non-existent ones, eternally pending all PRs.
- [2026-05-11] [Pre-Push Validation / Drift]: When a change adds, removes, or modifies tests (changing `test_count` / `suite_count`) or moves coverage by more than the 0.1% epsilon, the **same commit unit** must update the three living docs (`CLAUDE.md`, `README.md`, `docs/DEVOPS-HANDOFF.md`) BEFORE pushing. Running `node scripts/check-doc-drift.cjs` once early in the session and trusting that result later is wrong — the drift gate must be re-run after the last test/coverage change, not before it. **Why:** the v2.8 `docs-integrity` CI gate (single-leg, ubuntu/22) compares the docs against live measurement and fails fast; "validation passed earlier" ≠ "validation will pass on this exact tree." **How to apply:** Pre-push checklist for any branch touching `tests/**` or production code coverage: (1) run `npm run test:coverage`; (2) note the new test_count / suite_count / line_coverage; (3) run `node scripts/check-doc-drift.cjs` — if it fails, update CLAUDE.md / README.md / DEVOPS-HANDOFF.md in the same commit unit. For coverage value, store the CI-measured value (typically slightly higher than local) since the epsilon covers the macOS-vs-ubuntu delta in either direction. Triggered by: PR #28 `chore/harden-repo-coverage` pushed harden-repo tests that bumped 2,845→2,861 / 563→566 / 91.63→91.82 without updating the three docs; CI ubuntu/22 docs-integrity step rejected with 7 drift flags; required follow-up commit 1e868fc to clear the gate.

- [2026-07-12] [Review/Autonomy]: In autonomous runs, second-model review findings split into two classes with different handling. FACTUAL findings (wrong flag semantics, wrong paths, arithmetic errors, inverted source claims — anything re-verifiable against a file:line) are applied immediately WITH full disclosure of each finding + resolution in the delivery report. JUDGMENT findings (cluster moves, design overrides, scope changes — anything where a defensible alternative exists) are NEVER auto-applied; they surface as an unapplied checklist for the operator. **Why:** the first autonomous run applied 5 factual review fixes against a prompt that said "do not auto-apply"; the operator ratified the deviation but flagged it as exactly the behavior the design philosophy warns about. **How to apply:** before applying any review finding unprompted, ask "can I prove this with a file:line the reviewer cited?" — if yes and it contradicts nothing the operator decided, fix and disclose; if no, checklist it. Triggered by: 2026-07-12 review of the GSD-AUTONOMOUS-WORKFLOWS.md run.

- [2026-07-13] [Exploration Scope]: When a spec/design doc claims prior work already exists ("the 6 shipped workflows…"), verify that claim against `origin/*` branches and recently merged PRs BEFORE building — not just the working tree, and not only at the pre-ship `git fetch` gate. **Why:** the WORKFLOW-DESIGN doc asserted W1–W6 shipped; a working-tree-only Explore agent found no such files and reported "greenfield," so W1–W6 were rebuilt as a whole new `flows/` system — origin/main already had all six in a different (`workflow:<name>`) convention. The pre-ship divergence check caught it, but only after a full build + commit was thrown away. **How to apply:** for any "does X already exist / is this greenfield" question on an active repo, the exploration MUST include `git branch -a`, `git log origin/main`, and `gh pr list --state all` for the feature's keywords — a name absent from the working tree can still be shipped under a different filename or convention on main. Triggered by: 2026-07-13 W-workflows build, duplicate flows/ implementation discarded.

- [2026-07-13] [Ecosystem Audit]: A workflow with zero `subagent_type` spawns is NOT automatically an agent-wiring gap. Before recommending a command "should spawn agent X," verify against the workflow's actual design and git history — read-only interactive investigations (`/gsd:forensics`) and roadmap-bookkeeping commands (`/gsd:plan-milestone-gaps`) are correctly inline, and neither ever spawned an agent to "regress" from. **Why:** the crew coverage heuristic flagged both as gaps and the first expansion memo proposed wiring forensics->gsd-debugger (a code-bug debugger, wrong role) and plan-milestone-gaps->gsd-planner (duplicating the `/gsd:plan-phase` handoff it already defers to); reading the two workflows + `git log` showed both were inline-by-design false positives that never had an agent. **How to apply:** treat "spawns zero agents" as a question, not a finding — confirm the missing spawn ever existed and that a real agent's role/tools actually fit before proposing the wire. Triggered by: 2026-07-13 agent-expansion recommendation, items 1-2.
